# Define Actors as Effect services in an ActorSystem-owned environment

Actor implementations are Effect service definitions built from a static Layer, rather than mutable subclasses instantiated by the runtime. Each ActorCell builds that Layer in a dedicated instance Scope, closes and rebuilds it on restart, and passes its typed ActorContext explicitly to the resulting Behavior methods. ActorSystem owns a frozen Effect Runtime assembled during scoped acquisition with `ActorSystem.make().pipe(ActorSystem.provide(...layers))`; the system and child `spawn` APIs use its accumulated service type to reject Actor definitions whose required services are unavailable. This supersedes the base-class and protected-operation models in ADR-0029 and ADR-0030, and refines ADR-0031's lifecycle construction while retaining its decision that child creation belongs to ActorContext.

The alternatives were runtime-created mutable subclasses, an ActorFactory abstraction, and dynamically providing services after system acquisition. The service-and-Layer model fits Effect's Context, Layer, Scope, and Runtime directly: dependencies are acquired once per behavior instance, scoped resources are finalized on restart or stop, handlers are environment-closed, and missing capabilities become spawn-time TypeScript errors. Freezing the system environment prevents restarts from observing a different dependency graph and keeps shared resources alive for the ActorSystem lifetime.
