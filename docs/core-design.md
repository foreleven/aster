# Local Signal Delegation — Core Design

The accepted runtime and configuration boundaries are specified in [runtime design](runtime-design.md) and [ADR 0040](adr/0040-compose-aster-runtime-with-effect-layers.md). They supersede application-owned service assembly and direct environment loading described in historical sections below.

Status: working design. The local YAML and memory slice is implemented; wider persistence and delegation sections describe the intended system. The canonical terms are in [CONTEXT.md](../CONTEXT.md); the reasons behind durable decisions are in [ADRs](./adr/).

The upcoming Goal iteration selects local files for business Actor persistence: `~/.aster/actors/{path}/state.json` for current state and `~/.aster/actors/{path}/messages.jsonl` for ordered domain Messages, one JSON object per line. This replaces the proposed SQLite integration for that iteration. SQLite references below describe the previously designed and implemented Actor backend; adapting business Actors to the selected file storage remains implementation work. agentmemory retains its separate storage.

## Purpose and core model

The local system observes activity from connected services and the user's computer, recognizes when a Signal has occurred, and delegates the specified work to a local Agent. Signals may be user-authored or generated by an Agent to advance a user-defined Goal. Feishu IM, mail, tickets, monitoring alerts, and local workspace discovery are possible sources. Goal-driven behavior is an accepted design direction and is not yet implemented.

Everything addressable in the system is a persistent, path-addressed Context modeled as an actor. A Context can carry ordered messages, a mounted Channel, or both. Its path and state survive restarts. Agents processing a Context can inspect other Contexts by path; the precise access interface (MCP or skill plus CLI) is undecided.

### Public content and private actor fields

A Context's outward-visible content has two fields: `state`, a structured object, and `messages`, an ordered message list. Context reads also return the basic metadata `path` and fixed `description` alongside these content fields. Its implementation's other fields are private, including polling cursors, observed-ID tracking, scheduling flags, Channel objects, actor references, and service handles. Context reads, Agent snapshots, Signal evaluation inputs, and memory capture use this deliberately exposed representation.

Public `state` and `messages` are owned and updated by the Context actor. Private bookkeeping changes alone do not constitute a change to outward-visible content. Visibility and durability are separate: private data required for recovery can be persisted without being included in outward-visible Context content. Live handles remain scoped runtime resources.

Each Actor implementation declares the Schema for its public state object and public Messages and registers its own Context path in code. The public read representation is explicit; it does not serialize the Actor instance or automatically expose its private fields. The registry validates each registered path’s public State and Message Schemas, strips undeclared fields, and includes the fixed `description`. Public snapshots and change events are detached from actor-owned mutable values.

### Actor model

The actor implementation is local to one process and uses Effect 4 RC concurrency primitives rather than Cluster RPC. Every normalized Context path maps one-to-one to a local actor and persistence identity. Context paths are the public addresses; the ActorSystem keeps its `/user` runtime root, so `/lark` maps to `/user/lark` and `/lark/mail` maps to `/user/lark/mail` internally. Context descendants with virtual path segments are mapped to valid direct child Actor names by the Context layer, so their runtime paths need not be a literal `/user` prefix plus their public paths. An Akka-style hierarchical registry owns scoped actor fibers and in-memory mailbox queues. Distribution is not part of the current design.

This runtime lives in a domain-neutral `actor` module. It does not know about Contexts, Channels, Signals, or domain path conventions; the Context layer maps its concepts onto actor paths, references, protocols, and persistence identities.

Commands are transient mailbox messages. A handler validates a Command against current state and persists zero or more ordered Context Messages as events in SQLite. Recovery loads the latest checkpoint and replays Messages after its cutoff. The core does not persist all Commands or automatically replay an in-flight Command after process failure; scenarios needing reliable delivery implement their own delivery identity, persisted intent, and confirmation.

Context implementations may enable ReceiveTimeout in code; it is not user configuration. An idle actor passivates only when it is not handling a Command, its in-memory mailbox is empty, and it has no active children. This releases its scoped runtime resources without deleting the Context. A later Command activates it again from SQLite. Hierarchy removal is coordinated with concurrent delivery so a Command cannot target a stopped instance.

A Context actor holding an enabled Channel runtime remains resident so it can poll or listen for downstream data. It routes observations to child Context actors; those children may passivate under their own ReceiveTimeout settings.

Context paths also guide an Akka-style supervision hierarchy. A parent creates, holds, and supervises the Context actors it owns, including descendants whose public paths contain virtual grouping segments with no actor of their own. A child that passivates can be recreated by its actual parent actor; stopping a parent stops its active descendants but leaves all durable Context data intact.

Expected Command outcomes are handled inside the Actor behavior and expressed through its protocol, such as a reply or persisted Message. `receive` and `receiveSignal` have no typed error channel. Defects, persistence failures, and actor initialization failures enter parent supervision.

The default supervision strategy restarts only the failed child from its latest checkpoint and subsequent Messages, with backoff and a limit of five restarts within one minute. The failing Command is not automatically replayed; later Commands still in the runtime mailbox may continue. After the limit, the child stops and reports to its parent. A parent Actor implementation may select a different supervision directive when spawning a child.

Each Context is owned by one Actor implementation, which defines its State and Message Schemas, Commands, transitions, and interfaces in code. There is no string Context type tag or global Context Type catalog. Providers are shared integration dependencies; one Lark integration can supply several Actor implementations. Each Actor registers its own Context path and private processing behavior as it starts or initializes a dynamic Context.

Each Actor implementation defines a closed TypeScript Command union and exposes a typed `ActorRef<Command>`. Commands may contain local `replyTo` or actor references and do not require Effect Schema because they are not persisted. Persisted State, Messages/events, and checkpoints are Schema-defined. `ask` is a temporary reply-to interaction and cannot be recovered across process failure.

Actor handlers do not synchronously await another actor's `ask`. They end the current turn and route an eventual result back to themselves as a new Command (`pipeToSelf`), preventing mailbox starvation and cyclic waits. A scenario requiring this interaction to survive process failure persists its own delivery intent.

Each entity stores exact structured state separately from its Message history. Channel configuration, Signal definitions, and other machine-interpreted state remain exact. Message history consists of an authoritative Summary Checkpoint followed by uncompacted ordered Messages. A background Agent may summarize a committed Message prefix; after the summary is durably installed, the covered Messages may be deleted. This intentionally favors bounded local history and useful Signal detection over complete source-data archival without allowing lossy summaries to alter executable configuration. Effect mailbox requests are Context Commands, not domain Messages: a command can be rejected or append zero or more Messages. Mailbox persistence and Context state therefore solve different problems.

Each `ContextEntity` is a single writer: it serializes state-changing Commands and appends their Messages in order. Separate Context paths remain independently concurrent.

A Channel is a capability mounted on a Context and declares the child Context paths it can produce. Examples:

- `/lark/im` carries the Feishu IM Channel; chats are `/lark/im/chats/{oc_xxxx}`.
- `/User/workspace/` holds folders chosen by the user for workspace discovery; discovered workspaces have child Contexts such as `/User/workspace/{id}`. Discovery does not depend on Codex hooks.
- `/signals` supports human-configured Signal definitions at `/signals/{slug-name}`. Each triggering has its own record at `/signals/{slug-name}/runs/{id}`.

These paths express Context identity and navigation, not a separate Channel ownership hierarchy. A Context may carry both a Channel and messages.

The first concrete Context slice targets Lark email. Root Actors are registered through the ActorSystem API in application code: Memory, Signals, and Lark. The entry point knows only these roots. YAML supplies optional parameters for roots; its entries do not choose implementations or determine which Actors start. Each integration consumes its own complete configuration subtree and creates its own children. Lark owns the `children` configuration, validates `/mail`, and starts the mail Actor at `/lark/mail`. The application does not register or inspect Lark's descendants. Implementations can run with defaults when their configuration entry is absent. The current Lark default uses the CLI's selected profile and the `me` mailbox. This slice keeps Context state in memory; durable Context storage remains part of the intended system design.
For the first local email slice, `/lark/mail` uses the current user's mailbox (`--as user`, `mailbox: me`). Its actor polls for new mail and directly owns the discovered email actors at stable Context paths `/lark/mail/me/{message_id}`. Seeing the same `message_id` again addresses the same email Context. The `me` segment groups paths but does not require a `/lark/mail/me` actor. Later mailbox selection comes from configuration.

Historical email ingestion and backfill are outside the first slice. The mail Actor establishes its in-memory baseline on its first successful poll and creates Contexts only for newly observed IDs on later polls. Profile discovery and polling are owned by the integration; failures are logged and later polls can continue.

After a poll finds new message IDs, `/lark/mail` fetches their details in a batch and creates the corresponding email child actors. Each child keeps the sender, subject, plain-text body, and attachment metadata in its in-memory Context state, making the email readable for Signal evaluation. Attachment contents are fetched only when needed.

The Context layer provides relative-path child creation, for example `spawn("me/{message_id}", EmailActor)` from `/lark/mail`. It resolves the public Context path and encodes it as a direct child name accepted by the generic Actor runtime. The domain-neutral `ActorContext.spawn(name, ActorType)` remains a single-segment API and does not need to accept `/` in Actor names.

The first local configuration is loaded once at Aster application startup. The loader validates the outer structure and Signal definitions; integrations validate their own subtrees. File edits take effect after an application restart; hot reload is outside the first slice.

The configuration format is YAML, with `contexts` keyed by root public path and `signals` keyed by slug. The local `aster.config.yaml`, `.aster/` data (and legacy `.signals/`), and project-root `.env` are ignored by Git. The checked-in example is `aster.config.example.yaml`.

### Configuration evolution

The planned Goal iteration adds named model configurations under `config.models` for Goal-internal reasoning, including planning, progress assessment, and completion decisions. Each model configuration has a `name`; `config.goals.model` selects that named model for all Goals. Individual Goal definitions do not select a model, and the `config.goals` object can accommodate later global settings. Use pi core for Goal-internal Agent operation and its model adaptation, rather than a custom OpenAI-compatible-only loop. The exact model-entry schema and selected pi package release remain to be specified. The Goal's resulting delegated work is executed by Doubao. This configuration and execution separation is agreed but not yet implemented.

The local slice uses YAML, preserving the top-level `contexts` and `signals` mappings. Every Context gains a fixed, human-readable `description` of its basic identity, purpose, and relationship to the user. For configured Contexts, this sits beside `config` and optional `children` and is included in agent-readable Context content. User-authored descriptions in YAML are preserved during automatic processing. Descriptions for dynamically created Contexts are initialized by an Agent through the common processing mechanism described below and remain fixed as state and content change. The application loads YAML once at startup and resolves the memory data directory relative to the config file.

```yaml
contexts:
  /memory:
    description: My long-term memory
    config:
      dataDir: ~/.aster/memory
      port: 3111
  /lark:
    description: My work account
    config:
      profile: your-lark-cli-profile
    children:
      /mail:
        description: My work mailbox
        config:
          mailbox: me
          pollIntervalMs: 30000
```

The local slice integrates [agentmemory](https://www.agent-memory.dev/) as the memory implementation. It retains useful information learned from Contexts for later recall, with every submitted memory associated with its source Context path. Contexts retain responsibility for exact structured state, Messages, and actor recovery; agentmemory provides memory capture, recall, and consolidation. The agentmemory adapter is implemented in `packages/infra/src/agentmemory`; core owns the global Memory Actor and its durable capture workflow.

Upstream capture behavior and Agent adapters are recorded in [agentmemory integration findings](./agentmemory-integration-notes.md). The memory integration adopts the upstream automatic observation flow through the common Context processing mechanism.

### Managed memory runtime

By default, agentmemory is integrated into the application lifecycle. Signals installs a pinned agentmemory package as a project dependency and launches its CLI non-interactively on application startup. The CLI manages its pinned iii engine. Aster waits for the local memory service to become healthy, creates the global Memory Actor, and then starts integration actors. First startup may download the engine binary; users do not need to launch agentmemory separately.

The managed runtime is an Effect-scoped application resource. Application shutdown gracefully stops the memory worker and engine that it owns, while retaining the persistent data directory for the next startup. The configuration supplies runtime settings such as the data directory and port. Application-level Context processing sends information to the Memory Actor, which encapsulates the agentmemory REST protocol. The service remains a local subprocess even though its lifecycle is owned by Signals. External-service mode is deferred.

Memory configuration is declared at `/memory` under the top-level YAML `contexts` mapping, following the same `description` and `config` entry structure as other configured Contexts. The global Memory Actor backs this Context. Its configuration includes the managed data directory, port, and model settings; API keys are resolved from the project environment loaded from `.env`.

`/memory.config.llm` explicitly selects `provider` and `model`, with an optional `baseUrl` for providers supporting a custom endpoint. `apiKeyEnv` names the environment variable containing the credential. Application startup translates these settings into agentmemory's subprocess environment and ensures that the configured provider is selected. The key value remains outside YAML and agent-readable Context content. The following illustrates the agreed field structure; the actual backend and model are supplied by the user's configuration:

```yaml
autoCompress: true
llm:
  provider: openai
  model: your-model
  baseUrl: https://your-llm-service/v1
  apiKeyEnv: MEMORY_LLM_API_KEY
```

`/memory.config.autoCompress` controls LLM-written per-observation compression. It defaults to `true` when an `llm` is configured and can be explicitly disabled. Without an `llm`, memory capture uses agentmemory's synthetic compression. Startup maps the effective setting to `AGENTMEMORY_AUTO_COMPRESS`; enabling it with an LLM means each new observation is submitted to the model for compression. This is the application's default, while upstream agentmemory leaves LLM-written observation compression off by default.

The current local configuration uses MiniMax's China service: `provider: minimax`, `model: MiniMax-M3`, and `baseUrl: https://api.minimax.cn/anthropic`. Its key is referenced by `apiKeyEnv`; the example uses `MINIMAX_API_KEY`, while a local file may name an existing custom environment variable. Actual observation compression, session summarization, and memory recall have been verified with this service.

`/memory.config.embedding` is configured independently from `llm`. Embeddings are disabled by default, and recall uses BM25. An explicit embedding configuration enables vector retrieval with a local or remote provider. Startup enforces this choice even when the selected LLM's API key would otherwise activate upstream embedding auto-detection. The choice of concrete model and endpoint is supplied by the user's configuration.

### Account and mailbox discovery

The `/lark` Context actor retrieves the current account with `lark-cli contact +get-user --as user` and stores the account information in its exact Context state. The `/lark/mail` Context actor independently retrieves the current mailbox with `lark-cli mail user_mailboxes profile --as user --params '{"user_mailbox_id":"me"}'` and stores the mailbox information in its own Context state. Account and mailbox information remain associated with their separate Context paths and descriptions. Credentials remain outside agent-readable Context and memory content.

Each actor starts its profile query from its own `started` hook using `pipeToSelf`. A successful result returns through that actor's mailbox and updates its exact Context state. The email actor also starts its polling independently. Each behavior initialization, including a supervised restart, refreshes the profile once. These updates enter the same automatic processing mechanism as newly discovered email Contexts.

The previously agreed capture of discovered account and mailbox identity information remains part of initialization: the common mechanism sends these known profile facts to memory after they become available. Integrations update their Context state, and the application coordinates capture.

For the first slice, account and mailbox profile captures remain separate and use short memory sessions associated with their respective source Contexts. Each session captures that Context's public profile snapshot and ends after its memory input has been processed, following the same completion rule as the print-only Signal capture.

### Automatic Context processing

All Contexts use a common mechanism to trigger follow-up processing, including configured account and mailbox Contexts and dynamically discovered email Contexts. Their implementations populate or update their Context content; the Context layer automatically exposes the resulting creation or content change to application-level processing. Individual integrations do not explicitly submit information to the Memory Actor or opt into change publication on each write.

The application has one global Memory Actor that accepts information from this common processing flow and writes it to agentmemory. The application creates it before starting integrations. The common flow preserves the source Context path for each memory and makes Context information available for memory capture without depending on a later Agent session to encounter it.

For source activity such as chats and emails, memory capture is tied to an actual Signal triggering. Source Context state changes first enter System One screening; Message-only changes do not. Once the extraction Agent confirms a Signal has occurred and its Signal Run Context has been initialized, the common flow forwards relevant information through the Memory Actor to `/agentmemory/observe`. Ordinary source Context Message changes do not write memory on their own. The same policy applies to email activity represented in structured state; a Jev candidate alone is not sufficient for capture.

The memory input is a snapshot of the initialized Signal Run and its source Contexts at the time of that triggering. Each captured Context includes its public `path`, fixed `description`, `state`, and `messages`. These snapshots preserve the triggering's basis as it was observed; later source updates leave the captured input unchanged. Private Actor fields remain internal. The snapshots are passed to agentmemory for compression according to its configured mode.

agentmemory owns compression, indexing, and consolidation according to its provider and feature settings. Agents performing work can also use memory tools to save settled facts and decisions. Each Signal Run corresponds to one upstream memory session, keeping that triggering's captured information together. Actor activation, restart, and passivation preserve that association. The adapter translates the agreed snapshot content into upstream observation fields.

In the first slice, which prints proposed delegation, the memory session ends after its captured input has been processed. Ending the session requests agentmemory's session summary, subject to the configured LLM provider being available. This completes the memory capture batch; the Signal Run Context remains available for inspection under its own lifecycle. Session completion for a later version with real delegated execution is deferred.

The common change notification follows a completed content update, rather than merely spawning an actor with no usable content. For example, a new email becomes available for Signal evaluation after its email Context holds the fetched details. This mechanism also provides the entry point for initializing a dynamic Context's fixed description. Notification, Signal evaluation, and memory capture have their respective eligibility conditions.

Change notification is distinct from Signal eligibility. Signal Run changes continue to be excluded from triggering other Signals. Automatic follow-up processing also does not imply an Agent execution on every change.

`ContextRegistry` validates domain records and delegates canonical commits to `DurableContext`. The selected backend publishes each changed public representation only after storage commits; the Local implementation has no model requirement. Equal public writes and changes to undeclared private bookkeeping do not publish. The application processor initializes empty dynamic descriptions and follows private callbacks registered by Actor implementations to select memory captures and Signal evaluation inputs. It contains no Context type or path-based dispatch. Integrations do not submit memory commands; ordinary source activity remains outside memory capture.

### Memory recall

The memory slice exposes `aster memory search "<query>" [--limit N]` and `aster memory expand <obs-id> [<obs-id>...] [--session ID]` through the application CLI, following agentmemory's progressive disclosure. Search returns a compact envelope with at most 10 candidates by default and never automatically expands them. The Signal extraction Agent selects relevant IDs and requests their full details through expansion before using remembered facts. Expansion returns an expanded envelope, processes up to 20 selected IDs per call, and reports truncation. Both retain available source Context paths; consolidated-memory provenance is resolved on expansion. Recall uses agentmemory's search capabilities with the configured embedding mode; the memory service protocol remains inside the application adapter.

The extraction prompt documents both recall commands alongside `aster context get <path>`. The Context command reads the evaluation's scoped public snapshot; memory recall accesses the application's managed memory service. The later general MCP or skill-based Context access interface remains deferred.

### Fixed Context descriptions

An Agent initializes a dynamic Context's description using its path, a fixed identity hint supplied by its Actor implementation, and its parent Context's description. The hint is private initialization input; no type tag is part of public Context data. The description expresses what the Context represents and how it relates to the user. For example, an email Context at `/lark/mail/me/{message_id}` can be described as "An email in my work mailbox", using the description of its owning parent `/lark/mail`, "My work mailbox". The virtual `me` path segment does not require a Context of its own.

Description initialization is initiated by the common processing mechanism. Its inputs concern the Context's basic identity; changing state, message content, or current activity leaves the description unchanged. User-authored YAML descriptions also remain unchanged during automatic processing.

Human-authored Signal definitions have a dedicated top-level `signals` object alongside `contexts`, keyed by slug rather than full path. The Signals application starts the `/signals` root and maps each configured slug to a `/signals/{slug}` Context actor. This is a configuration-file convenience; a Signal remains a Context in the runtime model. Each definition has `when` (trigger-condition prompt), `task` (delegated-task prompt), `agent` (target local Agent), and `mode` (`auto` or `confirm`).

The first local slice does not invoke the configured target Agent for delegation. When a Signal is detected, it still creates an in-memory Signal Run Context at `/signals/{slug}/runs/{id}` and prints the source email Context path, task, target Agent, and execution mode for inspection. A real delegation adapter is deferred.

For each new email Context in the first local slice, Jev judges every configured Signal and returns candidate Signal IDs. One extraction Agent evaluates those candidates before creating any Signal Run. The first slice does not use BM25: with a small set of Signals, retrieval adds complexity and can drop semantically relevant candidates. Retrieval may be added later if the number of Signals or Jev cost warrants it. Printing replaces only task delegation, not Signal extraction.

The fast decision stage uses the System One protocol through `@typesafe-ai/sdk`. The top-level YAML `config.system-one` explicitly selects `url`, `model`, and `apiKey`, independently of Context configuration and memory models. The address accepts the service root, `/v1`, or the full `/v1/systemone` endpoint. An API key can be a literal or an exact `${ENV_VAR}` reference resolved after loading the project-root `.env`. These settings are required when Signals are configured; they are not part of public Contexts or Agent snapshots. Switching between TypeSafe and a compatible service such as Laya requires only changing these settings.

For the first email slice, Jev receives the new email's sender, subject, and plain-text body together with every configured Signal's `when` condition. The extraction Agent receives only the candidate Signal definitions and relevant Context paths; it can fetch Context details from the evaluation snapshot when needed.

The first extraction Agent runs through the installed `codex exec` CLI with a structured result. It evaluates candidate Signals; it is distinct from the configured target Agent whose delegated task is printed in this slice.

For this in-memory slice, each extraction evaluation creates a temporary, read-only snapshot of agent-visible Contexts. The extraction Agent receives Context paths in its prompt and reads the snapshot on demand through `aster context get <path>`. The CLI locates that evaluation's snapshot through its process environment. This allows the separate `codex exec` process to inspect Contexts by path without making the application's live memory directly accessible. The snapshot is scoped to one evaluation and removed afterward.

The first version reports a configuration error and stops startup if the loaded configuration cannot be used. Detailed recovery and partial-start behavior are deferred.

After loading YAML, the Aster entry point passes the `/lark` configuration subtree to `LarkIntegration.layer(config)`, provides that Layer to the ActorSystem, and starts the Lark root actor. The root uses the supplied configuration to create the Lark email child actor. Configuration is acquired as an Effect service for this startup lifetime rather than delivered later through a `Configure` Command.

## State-driven System One screening

The accepted change trigger is now public `state` changing for a Context actor, uniformly across actor implementations. Message-only changes, description updates, and private bookkeeping changes do not independently trigger System One. Equivalent state writes do not count as changes. This supersedes earlier references to generic Context content changes as the screening trigger; the first implementation is recorded in the current IM summary design.

An IM chat maintains a rolling summary in state. The summarizer combines the previous summary with a fixed new-message batch, retaining current progress, decisions, blockers, pending work, and key references. After the new summary is durably stored, covered messages can be removed; newer messages remain pending. A changed summary triggers System One Goal matching, followed by Goal reasoning. Ordinary summarization does not itself write long-term Memory.

The state-change trigger does not itself decide execution or authorize arbitrary Signal-to-Signal discovery. Initial-state handling, the relationship with independent Signal evaluation, and internal feedback routing are detailed in [the IM summary design](im-summary-design.md).

## Signal lifecycle

A Signal is a reusable Context, authored by the user or generated by an Agent to advance a Goal. It separately describes (1) when it should trigger and (2) what task to delegate, and specifies the target local Agent and whether each triggering requires human confirmation. It does not declare a fixed list of input Channels. Editing a Signal affects only future triggerings; an existing Signal Run retains the task, target, and confirmation requirement from its creation. The implemented email slice still uses only human-configured Signals.

A Goal coordinates a persistent Pi conversation, independent asynchronous Tasks, and Signals or timers. Users and owned feedback enter the conversation directly. Eligible Context changes pass System One screening and a separate Goal Agent relevance gate before entering Pi. Pi owns model/tool rounds, transcript persistence and compaction; Goal keeps business state and durable input handoffs. See [Goals](goals-design.md) for the current contract.

Work IM supplies Context updates through `/lark/im`. Initial history establishes source context; later changes can be screened for Goal relevance. Goal Signals observe conditions or timers and report occurrences to the conversation. Tasks use the shared Run/Delegation execution workflow independently of Signals.

The first validation Goal is the user's ongoing responsibility as Knowledge Engine frontend TL: continuously follow Knowledge Engine project progress. Its primary delegated output is a concise Doubao analysis when important project changes occur, covering the change, frontend impact, dependencies or blockers, matters requiring TL attention, suggested next steps, and source-message or document references. Analyses appear in the Goal conversation and do not complete this ongoing Goal.

The Goal Timeline exposes accepted inputs, delivery status and assistant responses. Public Context messages provide the business input feed, while Pi retains the native conversation. User messages enter the durable conversation queue. Already-running external Tasks retain their original input and continue independently.

The first Goal interface is a minimal local web client with a Goal list and status, conversation and execution progress/results, and a user-message input. Goal creation remains YAML-based. The frontend must be independently replaceable and consume a public backend API and message stream. It imports only browser-safe API contracts and Effect client/reactivity modules; it does not import Actor, core service or pi runtime implementations or access storage directly. Backend Goal and Agent execution does not depend on the page being open. The React frontend uses typed AtomRpc over NDJSON HTTP and SSE query invalidations. See [Reactive application API](reactive-api-design.md) for implemented contracts and lifecycle ownership.

The Goal's Pi Agent reads Contexts and memory, updates Goal progress through its mailbox, starts Tasks through RunRoot, and configures Signals through SignalsRoot. Task and Signal owners persist exact receipts before acknowledging their commands. Conversation completion does not end these peers.

Each Goal is managed by a GoalActor. All SignalActors, including those generated for Goals, remain children of SignalsRoot. GoalActors request their creation through SignalsRoot and watch associated Signals rather than owning them as children. Runtime watch retains its actor-termination semantics; separate business notifications carry progress and results. Signal occurrences and Task feedback use explicit durable Goal input commands. See [ADR 0039](./adr/0039-keep-all-signals-under-signals-root.md).

The first version does not reuse Signals across Goals. Each generated Signal serves only its originating Goal; independently user-configured Signals have no associated Goal. A Goal's later planning rounds adjust its own existing Signals to avoid duplicate definitions for the same work. Results return directly to that Goal without an additional shared-result relevance gate. This supersedes the earlier cross-Goal reuse proposal while preserving SignalsRoot's unified management boundary.

The user specifies a Goal's desired outcome or ongoing responsibility; completion criteria are optional. For a Goal with completion criteria, the evaluating Agent automatically determines completion against them using Context and execution-result evidence, and records its conclusion and supporting references in the Goal message stream. Successful completion of a delegated task alone does not establish that the Goal is complete. A Goal without completion criteria remains active until the user explicitly ends it; completion of an observed project or individual task does not end the ongoing Goal. When a Goal completes or is explicitly ended, it requests deactivation of its generated Signals through SignalsRoot to prevent further runs. Already-started delegations continue to completion and report their results to the Goal message stream. Deactivation is a domain state change and does not require immediately stopping a SignalActor and its executing descendants.

An eligible Context state change first passes a fast Jev decision that returns the IDs of Signals worth deeper evaluation. In the first slice, Jev considers every configured Signal; candidate retrieval is optional for a later scale-up. One Agent evaluation handles the candidate set for that change, may inspect other Contexts by path, and may determine that zero or multiple Signals have triggered. The Agent decides whether new information belongs in an existing Signal Run or warrants a new one. Jev does not make the deeper semantic judgment.

Automatic discovery is best-effort. Skipped information remains in its Context; later changes may be reconsidered, and the user may force an evaluation. A newly created Signal considers future changes by default; evaluating older Contexts requires an explicit backfill. Goal-derived Signals observe future Context changes or their configured timer; immediately actionable external work can be submitted directly as a Task. This does not imply a general historical backfill or bypass the trigger condition. Signal Run messages, including results, do not trigger other Signals through generic discovery; their explicit feedback to an interested Goal may cause planning and Signal adjustments. The exact construction and handling of messages after evaluation remains undecided.

## Readiness, confirmation, and delegation

Each triggering creates a persistent Signal Run Context with an ordered message history. Before work starts, Jev makes a separate typed decision about the whole run and relevant Contexts: executable with a selected Workspace Context, needs user input, or currently not executable. Workspace selection is part of this decision, not a fixed setting on the Signal. Uncertain workspace selection requires user input even for an otherwise automatic Signal. A request for missing information and the user's reply live in the run's message history; a not-executable result records its reason and can be reconsidered when circumstances change.

If the Signal requires human confirmation, confirmation applies to this run only. Otherwise a ready run may proceed automatically. A run is not silently delegated twice because the same information was processed again; an explicit user retry after failure creates a new Delegation Context. Each Delegation has its own persistent Context for execution progress and outcome. Confirmation, failure, and final result are also represented as messages in the Signal Run Context. Side-effecting failures are not automatically retried.

Results stay local by default. Replying in IM, updating a ticket, or taking other external action requires an explicit action in the Signal definition and goes through the relevant Channel. The means of submitting work to a local Agent and obtaining its eventual result may vary; waiting versus polling is not part of this core decision.

## Trust boundary

Evaluating whether a Signal has triggered does not by itself authorize editing its condition, task, target Agent, or confirmation requirement. Goal-driven planning adds Agent generation and adjustment of Signals based on an explicitly user-defined Goal; Goal-derived Signals use `auto` in the first version. External content does not gain authority to redefine the user's Goal. Since Agents can inspect Contexts by path, Channel credentials must never be present in agent-readable Context content. This is a design constraint; credential handling is not specified here.

For the first Lark integration slice, `/lark` configuration selects a `lark-cli` profile and relies on the CLI's existing credential storage. App secrets and tokens are not copied into the configuration file or agent-readable Context state. In a later phase, the Lark integration's `/lark` Context actor will coordinate token refresh; the domain-neutral Actor module remains unaware of Lark credentials.

## Memory and YAML slice scope

The following decisions are implemented in the local slice:

- YAML preserves top-level `contexts` and `signals`; root configuration contains optional `description`, `config`, and integration-owned `children`. Root Actors are registered in code and may start without entries.
- Context reads expose `path`, `description`, object `state`, and ordered `messages`. Other implementation fields stay private.
- `/memory` configures the default application-owned agentmemory runtime. Explicit LLM configuration resolves credentials through environment-variable names. Configuring an LLM enables observation compression by default; embeddings are a separate opt-in.
- The common Context mechanism coordinates initialization and content changes. Account and mailbox identities are discovered and captured separately.
- Source activity is captured only after an actual Signal triggering. Memory input is the triggering-time public snapshot of the run and its source Contexts.
- Each Signal Run has one memory session; in the print-only slice it ends after input processing. Initialization profile captures use their own short sessions.
- The extraction Agent retrieves compact memory candidates with `aster memory search "<query>"`, then expands only relevant IDs with `aster memory expand <obs-id> [--session ID]`, retaining available source Context paths.

Detailed retry protocols, external-service mode, and memory-session lifecycle for real delegated execution remain outside this slice. The Context actors remain in memory for local development; agentmemory owns its persistent memory data separately.

## Deferred decisions

- The detailed construction, routing, and processing of messages after Jev and Agent evaluation, including mailbox command shapes.
- The later durable and interactive form of path-based Context access (MCP or skill plus CLI).
- How changes arriving while a Delegation is running should be handled; no steer behavior is assumed.
- The exact mechanics of discovery, persistence, indexing, credentials, and Agent result collection.

## Context Actor definition and registration

Context-bearing Actors use `ContextActor.Service<Self, Services>()(key, { command, context: defineContext(...) })`. The `context` package owns this wrapper; the generic `actor` package remains independent. `Self.of` installs registration before the Actor's `started` callback and first mailbox Command. Business implementations do not call `ContextRegistry.register`.

Public Context paths are determined at spawn time. Ordinary paths follow the Actor hierarchy without its `/user` guardian. Virtual segments use `spawnContextChild`; an independent path such as `/delegations/{id}` uses `contextSpawnOptions(path)`. Spawn metadata preserves that path across behavior restarts, and child Context Actors inherit the parent's public path. Stopping an Actor does not erase its registry entry or persisted state/messages.

## Core and infrastructure package ownership

The former `context` package is now `@aster/core`. Core owns configuration schemas and validation, Context registry/actors, Signal and Goal actors, delegation lifecycle, description policy, and state-driven processing. Configuration is named CoreConfig. It depends on Actor, Agent and Effect, plus Node built-ins for value comparison and identifiers.

`@aster/infra` implements configuration-source loading, file storage and process locking, System One transport, Pi/Codex/Doubao execution, and the agentmemory backend. `@aster/integrations` owns Lark and generic mail. Neither package imports or re-exports the other; the local host selects their Layers separately. Core owns Memory contracts, the Actor and capture workflow, while infra provides its `MemoryBackend`. See [ADR 0046](adr/0046-separate-business-integrations-from-infrastructure.md).

The local application now contains only CLI/startup assembly, HTTP/SSE/static-file delivery, and process shutdown. App-specific `.env` and CLI executable paths are explicitly supplied to Codex adapters; package-relative paths are not used. Core's Signal screening accepts ContextRecord for any source rather than importing Lark's EmailData.

Domain tests live with core, infrastructure adapter tests with infra, business transport tests with integrations, and cross-integration and HTTP tests with the local app. All imports, package names and build ordering use core; no compatibility context package is retained.

### Business policy versus adapters

Goal planning prompts/tools and completion validation, Signal extraction prompts/result validation, and whole-Signal execution decisions belong to core. Depending on the shared Agent abstraction does not turn business policy into infrastructure. Infra owns execution/decision SDK transport, subprocesses, filesystem access and executor capability descriptions. Integrations owns business-system transports and workflows. Core does not import integrations. The app assembles the Goal runtime directly; there is no second integration-owned Goal runtime. Source folders group files by capability, retaining root package exports.

## Explicit Context revision admission

All Context writes now use `ContextRegistry.commit(record, { expectedRevision })`; the implicit-revision `set` helper is removed. Legacy persisted records remain readable at revision zero. Domain owners capture one snapshot before deriving a transition and carry that snapshot's revision through asynchronous work. In particular, Goal working-state projection must not reload a newer revision after awaiting history counts/pages and attach it to an older computed state.

Description initialization also receives an explicit observed revision. It can fill a missing description but cannot overwrite concurrent state/messages. A stale revision fails with typed ContextConflict and emits no change; callers may refresh and decide whether to retry. New caller-driven operations retain their supplied revision, while mailbox-owned observation transitions use the snapshot read by that handler. Actor persistence/ownership failures enter supervision; expected tool validation and version conflicts become protocol errors. Storage failures must never be formatted as a successful tool reply.

This storage-boundary migration does not complete the shared command envelope, stable request receipts, causation propagation, or durable reaction outbox requirements. Those remain separate domain changes.

## Controlled Personal Signal commands

Personal accepts a Signal proposal through `ApplyPersonalSignal`, or as part of a structured model reply. Its mailbox persists an outbox intent before delivery; model replies, completion cursor and proposed intents share one commit. The envelope carries operation, requestId, causationId, source, target, expected target Context revision, creation time, full definition and active state. The Personal admission revision and the target Signal revision are distinct.

The Signal mailbox owns create/update validation and commits the definition with an exact-payload receipt. The reserved `personal--` namespace and persisted `/personal` owner prevent cross-owner updates. YAML/Goal definitions remain outside Personal's write authority; the legacy Configure/Upsert protocol returns a typed rejection if it targets a Personal Signal. Retrying an identical request returns the original receipt before checking the current revision and does not reset a timer. A changed payload under the same request ID conflicts.

A full update can add or remove schedule/notBefore and activate or deactivate the Signal. No schedule means source-change screening; once and cron use the Signal timer path. Accepted updates increment the timer generation independently of the Context revision, invalidating stale ticks. Personal lists only configured executor names, never their credentials. Personal Signal Runs use confirm mode and enter the existing ApprovalQueue flow before execution.

Each due cron occurrence is a new bounded causal root, identified by the persisted Signal path, definition revision and due time. The accepted recurring definition authorizes this renewal; it does not renew authority on message delivery, acknowledgement, or replay. Each root permits at most four Agent turns and remains subject to the receiver's eight-admission branching bound. This prevents a long-lived monitor from exhausting its creation request's lifetime budget. Immediate reactions and one-shot follow-ups retain their parent chain, so repeatedly creating one-shot timers cannot replenish it. The occurrence's root is persisted before delivery and reused after recovery. Deactivation, deletion, Goal completion and stale timer revisions still prevent new occurrences.

Outbox attempts and lastAttemptAt commit before remote submission. Unknown acknowledgements retain the original operation for receipt reconciliation, including after restart. Success clears stale delivery errors. This reconciliation is safe because the receiving owner deduplicates the exact persisted request; it does not authorize retrying an uncertain external execution. Generalized SystemOne reactions, notifications and execution policy remain separate work.

## Personal approval response admission

Explicit user decisions enter Personal through RespondPersonalApproval; model results cannot contain approval proposals. Personal persists the request envelope in its outbox and returns its own admission revision. ApprovalQueue receives the exact request, validates the current pending entry and question/decision constraints, and commits its response, ordered resolution event and command receipt in one Context write using the caller's approvalsRevision. The trace records requestId, causationId, source, target and committed revision. Goal, Signal and Approval delivery receipts share CommandReceipt.

An identical replay returns its original ApprovalQueue receipt even after acknowledgement or unrelated queue changes. A changed payload under the same identity, stale revision, resolved/revoked request or invalid answer cannot produce another resolution. Legacy Enqueue/Resolve/Acknowledge/Revoke updates preserve command receipts. Queue acknowledgement is distinct from external response delivery and execution completion; this command grants no standing Signal authority and does not retry an uncertain external submission.

The browser freezes the explicit decision until admission is reconciled. It stores this identity at application-session scope, so navigation and SSE refresh cannot change it. Once Personal admission is known, the persisted outbox becomes the delivery view. A rejected domain response remains visible and requires a new explicit user command. Browser state alone does not survive a full document reload; committed outbox entries do.

## Personal one-time Tasks

`RunRootActor` adds an independent `/user/runs` owner for Personal’s prepared Tasks, while Goal and Signal Actors retain their Run children. `StartPersonalTask` uses Personal’s durable command outbox and a stable hash-derived Run path. The Run atomically commits exact Task admission and its receipt before readiness. Confirmation remains mandatory. No Signal is synthesized or persisted for this operation.

### Canonical state and public read views

Context storage is authoritative owner state; it is not itself an Agent-readable contract. Each owner declares an explicit read policy. Core supplies its domain policies; integrations register their own path families and may override them for a registered ContextDefinition. Schema decoding selects allowed fields recursively. Missing policy or invalid state returns a restricted metadata-only record, not the canonical state. Read projection is detached and does not mutate recovery state or advance revision.

The API and Personal command boundary, Goal Context catalogue and Signal tools, Task preparation/readiness, Context reactions and memory capture use these read views. Run views omit frozen raw source snapshots; Delegation and Approval views omit provider metadata and session handles; Memory views omit pending capture batches. Native tool calls/results and provider blocks remain in execution history but do not cross public Context/history reads. History pages retain canonical total/sequence and advance the cursor through filtered entries. Text, descriptions and prepared Task evidence are authored business content, not an automatic secret-scanning boundary.

## Processing recovery boundary

SystemOne and notification delivery expose operator diagnostics through InspectProcessing. RecoverProcessing accepts a stable request ID and expected owner revision, then routes the typed recovery command to the owning Actor. The Actor persists authorization and its receipt with the pending transition before acknowledging. Exact replay returns that receipt even after later owner revisions; changed request reuse or stale new authorization is rejected. RetryScreening applies only to failed work and retains its admitted source/catalogue. RetryReactionDelivery and RetryNotification apply only to selected unknown deliveries and retain their original command identity. Successful decisions and known rejections cannot be overwritten through recovery. Context projection excludes frozen evidence and private recovery journals.

## Context queries

`ContextQueries` is a core-owned routing port for read-only, on-demand integration commands. Runtime creates one service shared by integrations, Goal reasoning, Personal and the application API. Integrations register handlers in their owning Actor scopes; inactive or retired routes fail explicitly. The contract carries a public Context path, a command name, named scalar arguments and a JSON result with query timestamp. Each adapter owns its command allowlist and argument schemas; core has no dependency on concrete apps or OpenCLI.

Goal and Personal expose `query_context` and `read_query_result`. An evaluation caches result pages so large evidence can be read without rerunning external queries. Existing Context discovery remains the entry point for finding the adapter's command catalogue. The `QueryContext` RPC uses the same routing port. Queries do not authorize external mutations, delegated execution or booking. Query evidence is untrusted data, and its links/timestamps must be retained when reasoning about prices or availability.

Personal and Goal prompts treat user-requested research and planning as authorization to use relevant read-only Context queries in the current invocation. Missing optional preferences refine recommendations rather than blocking all investigation. Agents first gather evidence and offer provisional options with explicit assumptions, then ask the few questions that affect the next choice. They do not create delegated Tasks merely to access available query tools. Source failures limit the claims and may require user intervention, but do not prevent independent research. Existing approval requirements for external mutations and delegation remain in force.
