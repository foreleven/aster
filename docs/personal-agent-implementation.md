## Versioned commit boundary

New command handlers use `ContextRegistry.commit(record, { expectedRevision })`. Creation expects zero; each public content change increments revision. An identical write with the current revision returns the existing snapshot without a write or notification. A stale identical write still conflicts. Schema validation and conflict errors do not mutate state. A storage failure may have committed its pending intent: the path rejects further writes until Actor registration reloads and validates the authoritative store. Recovery rejects a missing previously committed record or a regressed revision.

Unversioned persisted Contexts read as revision zero. All registry writes now require an explicit expectedRevision; legacy `set` has been removed. Owner-derived transitions bind their revision to the snapshot used for computation. Versioning every caller-facing domain command and propagating shared receipts/causation remain outstanding. Recovery notifications currently suppress source evaluation like bootstrap; a durable outbox must ultimately recover undelivered reaction intents.

Tests: `packages/core/test/context-commit.test.ts` covers competing writers, stale/no-op writes, validation, storage fencing, legacy recovery, and lost commit acknowledgement. `packages/infra/test/storage.test.ts` checks persisted revision and pending-file replay. Goal restart fixtures now implement an actual retained store so recovery tests can read their committed state.

## Pi prototype gaps to resolve

- Freeze the exact input range and request payload before handoff. Currently pendingRequestId is durable but the input range is read afresh; recovering an old request must not acknowledge messages that arrived after its original submission.
- GoalActor now saves the applied summary/status, cursor, and cleared request in one Context commit. The separate GoalHistory conclusion append and cross-Actor outputs still need a durable result/outbox protocol.
- Settled result collection now uses paginated entry bounds, including the terminal tool round when Pi's answer points to the assistant tool call. Tests cover replay after later requests and repeated tool-call IDs.
- Durable provider requests use the configured native compaction budget. AgentConversations owns the injected writer; unknown-outcome fencing protects generation and recovered compaction. Custom context transforms are not exposed.
- Model known run failure, unknown handoff outcome, retry identities and manual reconciliation explicitly. Do not leave a failed request permanently reused or blindly resubmit side effects.
- Cancellation now joins the full SDK invocation through Harness.close before releasing the Effect scope, verified with a gated SDK close. Cross-process owner locking/fencing and unsafe-tool recovery outcome tests remain required.
- Separate structured evaluation/result projection from native transcript and legacy GoalHistory text. Pi result persistence must precede Goal application, and cross-Actor operations need idempotent receipts.

## Personal command ingress

`PersonalAgentActor` owns `/personal` and is spawned by `AsterRuntime` as `/user/personal`. Its local Context has no model dependency. `Accept` validates a business request ID, causation ID, expected revision, and text; the server fixes source/target to user and `/personal`. One versioned Context commit appends the ordered `PersonalMessage` and its pending request identity. Only then does the Actor return a `PersonalReceipt` (request ID, committed revision, sequence).

An identical retry returns the original receipt before checking the now-stale revision. Reusing an ID with different text or causation fails with conflict. New inputs with stale revisions fail without appending. A storage acknowledgement failure enters supervision; the caller receives no success and must reconcile with the same ID after recovery. `GetPersonal` and `SendPersonalMessage` are typed RPCs using a business request ID separate from the RPC transport ID. Public reads through `ReadContext` and `ListContexts` return detached snapshots, never storage handles.

When `config.personal.model` is configured, the runtime supplies `PersonalProcessor` and the Actor drains accepted inputs one at a time. Before invoking the processor, it commits a running attempt with the exact input sequence and execution identity. New user messages remain independently queued while that attempt runs. A generation-tagged result returns through `pipeToSelf`; the mailbox commits the reply, attempt outcome, processed input cursor, and queue removal together. The public feed contains business `UserInput`/`AgentReply` records, not native Pi frames.

The processor currently uses the existing `Agent` durable prototype behind a domain service. It owns a separate Personal Pi conversation under `~/.aster/personal/personal/pi` (or `config.personal.storageDirectory`), uses controlled mailbox reads with paginated tool output, and submits a structured reply. Read tools and the result tool are replay-safe; it has no mutation tools. Its result may propose up to ten user-requested Goal messages, with target revisions. The mailbox commits those outbox intents atomically with the reply and attempt outcome before any delivery. Signal operations and durable backend adapter seams are implemented in the later slices below. Task execution, approvals and ownerless session migration remain incomplete.

Failures remain visible as failed attempts and keep the input pending. Duplicate input acceptance and restart do not silently retry failures. `RetryPersonalInput` explicitly starts a new read-only attempt with a distinct execution identity and expected revision. Duplicate retry IDs return their original receipt, including after completion; conflicting reuse is rejected. Previous failed attempts remain queryable. A running attempt recovered after interruption reuses its saved identity, allowing Pi to return an already committed result before the Actor applies it. When no Personal model is configured, the durable inbox remains available without starting model work.

Verified locally with real ActorSystem instances and fake storage: full runtime restart, duplicate/conflicting requests, concurrent stale revisions, commit-before-ack ordering, lost commit acknowledgement, explicit snapshot reads, absence of automatic ContextChange ingestion, runtime readiness, and an HTTP RPC round trip with distinct transport IDs for one business request. `pnpm check` and `pnpm test` passed after this slice (222 backend tests: Agent 10, Actor 40, Core 81, Memory 10, Integrations 25, Local 56). Core and Local Effect diagnostics report zero errors and warnings.

## Personal-to-Goal outbox

`SendPersonalGoalMessage` accepts an operation ID, causation ID, Personal expected revision, Goal slug/revision, and message text. The server fixes the source to `/personal`, derives the Goal target, and freezes the creation time. It commits a `pending` outbox item before returning the source receipt. Model-proposed messages enter the same outbox in the result-application commit. Personal never calls a Goal repository; the runtime binds `PersonalActions` to the Goals root, and asynchronous acknowledgements return to the Personal mailbox with generation checks.

Goal's `Deliver` command validates its envelope and expected revision, then commits the input, receipt, and pending evaluation intent in the Goal Context. Receipt lookup precedes CAS checking, so an identical redelivery returns the original committed revision. Reusing an ID with changed content or sending a new stale command is rejected. The compatibility GoalHistory feed is an idempotent projection: identified appends deduplicate across in-memory/file-store restart and reject different content under the same key. If projection fails after append, Goal recovery completes it once before evaluation. A duplicate accepted delivery does not schedule a second evaluation.

The source records `delivered`, `rejected`, or `unknown` outcomes. Missing acknowledgement is `unknown`, never proof of rejection. Recovery requeues unknown internal Goal deliveries using the original identity; an identical explicit resend also reconciles an unknown outcome. This retry rule depends on the receiving Goal's persisted dedupe contract and must not be applied to arbitrary external writes. The current route has a fixed Personal source and Goal target, and neither side forwards raw ContextChange to Personal; broader notification/outbox loop control remains pending. Public outbox records are available through Personal's Context snapshot and the Context workspace UI described below.

## Freeze the Goal history admission boundary

A durable Goal now persists `pendingHandoff` with its request ID, evaluation reason and admitted history upper bound before invoking the reasoner. Every history page and compaction pass for that request is capped at that boundary. Restart reuses the same request, reason and bounded prefix; it does not append a new start event or consume messages accepted after the original handoff. Later input keeps a separate pending-evaluation flag, so applying the recovered answer advances only the original cursor and then schedules the next batch. ## PiDurableContext transaction adapter

The concrete integrations adapter uses Pi 1.0.0 Session without a model or Harness. Local and Pi share core's canonical CAS/notification/recovery kernel. Each accepted Pi Context revision atomically stores a full `app.aster.context.commit` business entry, the typed snapshot document, and a session index containing mappingVersion, shardId, path, conversationId, revision and entryId. Receipts, outbox and ordered messages remain inside the full snapshot. Full snapshots deliberately model message replacement as well as append; entries have no model frames.

Opening validates all persisted mappings, resolves SDK-branded IDs from real conversation records, and checks latest business entry/document/revision agreement. Failures reject acquisition instead of silently creating replacement state. Any commit failure fences the shard's driver; reconciliation closes the old Session, opens a fresh handle and validates committed storage before permitting another write. A lost acknowledgement after write recovers the new revision, while rejected writes recover the old revision. No-op retries do not append duplicate entries. An admitted commit drains before cancellation releases the Session.

`PiDurableContext.layer({ directory, shardId })` provides the injectable backend. Its directory lock covers opening, mutation, recovery and finalization; JSONL uses fsync. The Pi lock deliberately refuses stale-lock reclamation because unlinking an old lock can race another acquiring process. Recovery after an unclean process exit therefore requires explicit ownership reconciliation; automatic crash-safe lease/fencing remains unfinished. The test driver factory requires a fresh storage handle per open and an externally held exclusive lease. Production continues to use FileDurableContext; no existing runtime data is migrated.

This completes the storage transaction slice only. Task-owned conversations, PiDurableAgentRuntime, ExternalAgent/Task execution input construction/History integration, unsafe tool replay, external unknown outcomes, backend routing/rollback and the other P0/P1/P4 requirements remain open.

## Configured routing, offline migration and rollback

The local host now provides `ConfiguredDurableInfrastructure`: longest segment-prefix routing selects exactly one Local/Pi writer per Context. Optional Pi execution shares the selected Pi Context owner; without a model, Pi storage remains a plain Session. Startup validates every retained copy and rejects missing/stale selected state or equal-revision divergence. It persists routing authority in a private fsync-backed journal and rejects config changes until offline migration has published them. Default routes remain Local.

`aster storage migrate --config FILE` captures configuration without starting Models, Harness, AsterRuntime or integrations. It holds the same configured root lease as application startup, plus the Pi lease; validates the entire plan before importing; preserves full state/messages/receipts/outbox and original revision; reopens Pi and rereads Local for disk replay validation; then publishes authority with a generation audit. Unversioned records migrate as revision zero. Reverse routes use the same protocol and carry newer Pi records back to Local. All Pi identity/directory settings are retained after rollback. Directory relocation and native agent-session migration are explicitly outside this operation.

Startup captures LocalConfig once around the whole program, resolves `config.durable.root` before acquiring the process lock, and keeps that lock through runtime finalization. Goal history and screening journals now follow that same root. Relative storage paths resolve beside the config file. Pi storage cannot overlap Local, authority or journal directories. Runtime owner preflight validates existing Context identity before writing execution-owner metadata, so opening a Context-only archive with a wrong owner leaves it usable by its original owner.

Run UI displays publication separately from local completion, with target navigation, identity, exact content, approval navigation, receipt and retained uncertainty. Reconnect refreshes current state. There is no retry button that could repeat an unknown external write.

## Native durable conversation rewrite (2026-10-08)

This update supersedes the historical exchange ledger, tool fencing and adapter steering policies recorded above. DurableHarness now exposes a scoped conversation with native submit, lookup, wait and explicit abort capabilities. Pi owns checkpoint recovery, tool replay, steering queues and compaction. Goal reads the persisted assistant answer directly. Task owns delivery markers and round coverage in its execution journal. The agent adapter no longer reconstructs generated message ranges, stores parent/steer receipts, blocks all placed submissions during reconciliation, or implements a global unknown-tool fence. External executor uncertainty and business idempotency remain in core. See the agent package README for current scope and cancellation semantics.
